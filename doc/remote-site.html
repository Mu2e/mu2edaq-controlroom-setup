Remote Control Rooms

Remote institutions watch the control room screens with remote-site/. Each site has an overlay remote-site/sites/<site>.yaml (login account, view-only, extra screens) and settings remote-site/sites/<site>.env (Kerberos identity, keytab path, viewer, password files, launchers). The full guide is remote-site/README.md.

Install

remote-site/install.sh --site caltech
remote-site/crs-screen --site caltech --check

The installer checks prerequisites, makes venv/ with PyYAML only (or reuses the one from bootstrap.sh), checks the overlay, finds a VNC viewer, installs ssh-selector from a sibling mu2edaq-cluster-tools, checks keytab and password file permissions, and makes the launchers: .desktop entries on Linux, apps in ~/Applications/Mu2e on macOS. It never runs crs-remote.

Use

remote-site/crs-screen --site caltech shift-main cr01
remote-site/crs-nodes --site caltech
venv/bin/crs-tunnel status --site-config remote-site/sites/caltech.yaml

Site overlays

Only crs-tunnel reads overlays: --site-config FILE (repeatable), else CRS_SITE_CONFIG. Allowed keys are personal_user, gateway (last file wins; CRS_GATEWAY beats both), view_only (true in any file wins) and sessions. Added sessions are unmanaged: crs-remote ignores overlays and refuses unmanaged sessions, so a site's screens are never started or stopped by these tools. Repeated names, local ports or host displays are errors naming the overlay.

macOS

Screen Sharing cannot be view-only or read a password file. With --view-only, --password-file or a view-only overlay, crs-tunnel connect uses TigerVNC Viewer.app and stops before launching anything if it is missing. Plain crs-tunnel connect still opens Screen Sharing.

View-only

View-only prevents accidental input from a remote room. It is not a security boundary: real enforcement would be a separate view-only VNC password on the DAQ hosts.
